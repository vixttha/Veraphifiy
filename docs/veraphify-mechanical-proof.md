# Veraphify mechanical proof plan

This is the project plan for `Lydite-Test-Vault`, the long-lived branch for Veraphify's test vault. The branch was seeded from the full [published Lydite v0.0.4 template](https://github.com/vixttha/Lydite-Test-Vault-Template/releases/tag/v0.0.4), upstream commit `87d25d80d3154d295052412b64b29a0f0f152c27`, tree `4f697f230b98a3e3c5688dd107b2f53dd5e9a795`. The upstream inventory contains 14 languages. Their shipped samples exercise the template. The Veraphify cases below are proposals.

## Product baseline

Test the real [Veraphify CLI](https://github.com/vixttha/Veraphify/blob/92ec58f3e574efd814f395d2f2bc23948d794b55/veraphifiy.mjs) at a pinned full Git SHA. The starting baseline is the [v0.0.9 integration candidate](https://github.com/vixttha/Veraphify/pull/56) at `92ec58f3e574efd814f395d2f2bc23948d794b55`. Its [existing Graphify Test Vault](https://github.com/vixttha/Veraphify/tree/92ec58f3e574efd814f395d2f2bc23948d794b55/test-vault) covers the producer, MCP, handoff, and initial Veraphify archive replay in six languages. The [public push run 44649433106, attempt 1](https://github.com/vixttha/Veraphify/actions/runs/44649433106/attempts/1) passed its three jobs. The [release tracker](https://github.com/vixttha/Veraphify/issues/21#v009-release-evidence-rule) owns release acceptance.

Use the [two-version walkthrough](https://github.com/vixttha/Veraphify/blob/92ec58f3e574efd814f395d2f2bc23948d794b55/docs/adopter-walkthrough.md) and its pinned Graphify producer as the first fixture. Make two synthetic Git commits. The same feature must resolve to `src/feature.py:3` in `v1.0.0` and `src/feature.py:4` in `v1.1.0`. Derive expected source SHAs and line anchors from the fixture's committed bytes independently of Veraphify. Preserve a copy of the original archive entry for byte comparison. Record the trusted source SHA and archive digest in the test harness before replay.

## First case for each language

| ID | Language and ownership | Observable pass condition | Order |
| --- | --- | --- | --- |
| VFY-JS-001 | **JavaScript** owns the native Node CLI contract. | Import both fixture versions through the CLI. A byte-identical repeat of the first import succeeds. A different import targeting the same project and version fails and leaves the original entry unchanged. `verify` and `lookup` with trusted pins return both expected source SHAs, archive digests, and version-specific citations. Wrong pins and missing versions fail. | 1 |
| VFY-PY-001 | **Python** owns independent evidence verification. | Recompute the archive and embedded receipt digests, compare decoded source bytes with `git cat-file` at the pinned commit, and verify the exact export on a second checkout. Reject a handoff with a changed byte, wrong workflow identity, or mixed-attempt receipt using the existing receipt tools where applicable. Keep the digest of the ZIP distinct from the archive digest reported by the CLI. | 1 |
| VFY-SH-001 | **Bash** owns the published Linux walkthrough. | Execute the documented commands from a clean checkout with pinned prerequisites. In an unrelated working directory with spaces, direct stdout remains machine-readable, a missing version puts the diagnostic on stderr and exits nonzero, and a failed command propagates a failing status through the actual runner pipeline. | 1 |
| VFY-PS-001 | **PowerShell** owns the real Windows shell boundary. | Invoke all three commands on standard Windows with literal paths containing spaces and brackets. A successful lookup yields one JSON object. An explicitly wrong pin produces the expected diagnostic on stderr and a nonzero native exit code. The retained Ubuntu archive replays with the same SHA-256 on Windows. | 1 |
| VFY-TS-001 | **TypeScript** owns typed consumer contracts. | Decode real `lookup` stdout before exposing it to a consumer. The valid result has a version, source pin, and typed path and one-based line. Runtime rejects a malformed line or missing pin, and pinned `tsc` reports the intended diagnostic for a consumer that treats an unresolved result as a citation. | 1 |
| VFY-GO-001 | **Go** owns concurrent subprocess behavior. | Against one temporary archive, coordinate simultaneous same-version imports with identical and differing inputs. Identical contenders agree on the final digest. Conflicting contenders yield one consistent archive and a clear refusal for the loser. A concurrent reader may report an absent entry before publication and must only see a complete pinned entry after it. | 2 |
| VFY-RS-001 | **Rust** owns independent byte-format conformance. | A strict reader accepts a real archive and agrees with independently pinned byte counts and hashes. Compare its acceptance with `verify` on valid archives at the documented aggregate 8 MiB source boundary and above it, and on a noncanonical Base64 value. Check the intended rejection path with a control that passes any outer digest gate. | 2 |
| VFY-CPP-001 | **C++** owns native source-coordinate verification. | Read committed source bytes through an independent byte-oriented line scanner. For UTF-8 source with LF, CRLF and a missing final newline, compare the physical line numbers and exact source slices with real `lookup` results and embedded blobs, even when the working tree's bytes differ. | 2 |
| VFY-FS-001 | **F#** owns the archive state model. | Generate seeded sequences across versions and projects containing import, repeat, conflicting import, verify and lookup. Compare the observed CLI results and on-disk digest after each operation with a small immutable reference model. Preserve the seed and minimal failing sequence. | 2 |
| VFY-HS-001 | **Haskell** owns the graph-semantics reference. | Use a pure reference function over small producer fixtures to derive implementation citations from graph relations. Compare those sets with real `lookup` outputs for direct implementation, documentation and test edges, and features with no implementation citation. Validate the owner's intended behavior for ambiguous cases before locking expected results. | 2 |
| VFY-CS-001 | **C#** owns Windows file-sharing behavior. | Use a .NET process to hold an existing archive entry with an explicit sharing policy while invoking Veraphify. Assert the documented/native outcome for permitted reads and denied reads. After the lock is released, the same original entry still verifies and the conflicting import cannot replace it. | 2 |
| VFY-JAVA-001 | **Java** owns JVM client interoperability. | Call `lookup` with `ProcessBuilder`, decode stdout as UTF-8, and deserialize the actual output. A fixture with non-ASCII source paths and two exact version strings survives round-tripping without changing the path, version, full commit SHA or numeric line. | 3 |
| VFY-RB-001 | **Ruby** owns the batch-adopter workflow. | Use `Open3` to run a table of projects and versions in one archive. Project case aliases resolve consistently, distinct projects with the same version remain isolated, and an expected error in one row stays attached to that row while later rows complete with their original pins. | 3 |
| VFY-LUA-001 | **Lua** owns the editor navigation boundary. | Feed real `lookup` output to a headless Lua or Neovim adapter. It opens the expected file at the exact one-based line for each selected version. An unresolved feature produces no navigation. Record this as optional adopter coverage unless an editor integration is shipped. | 3 |

## Execution and evidence

1. Start with the existing six-language Vault. Add JavaScript archive lifecycle assertions, Python evidence checks, Bash and Windows invocation checks, and the TypeScript consumer contract. Place Go concurrency in the next pass. Keep one case ID and one owner per assertion. Reuse the existing two-version producer and replay flow before adding fixtures.
2. Use standard public GitHub-hosted Ubuntu and Windows. Run the candidate checkout and the Vault harness at separately pinned full SHAs. Keep an extra runtime out of the release-critical jobs until it guards a documented product claim or catches a demonstrated regression. Add an optional consumer job when its actual integration is ready.
3. For each case, record the real command, fixture and control, expected result, observed result, and named native outcome. A negative case must reach the intended product assertion and verify its diagnostic or preserved state. Count skips and blocked cases separately from passes. Generic Lydite samples establish template health only.
4. Publish synthetic evidence only. Record candidate SHA, Vault SHA, workflow path and revision, event, ref, run, attempt, job and runner, artifact ID and ZIP digest, and the per-entry archive digests. Validate downloaded handoff bytes in the independent readers before replay. Apply the repository's push and same-attempt rule for release proof.
5. Track each case as planned, implemented, or verified against the intended checkout. Advance the first batch when `import`, `verify`, and `lookup` each have a verified valid path and a verified failure or boundary path, and the two-version archive replays on both operating systems.
