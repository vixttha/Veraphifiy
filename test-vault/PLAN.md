# Graphify HQ Test Vault plan

**Status: Proposed.** The 40 cases below cover 22 Python, 6 Bash, and 12 JavaScript cases. The original 12 case IDs carry over from the original Vault plan. The [case catalog](cases.md) opens when implementation begins. Where a pinned source already has a regression, register or extend it when the corresponding code is adopted.

## Python · unittest

Owns Graphify behavior and on-disk recovery. Use the real evidence builder and Graphify MCP for the graph cases. Reuse the publication tests already in BART #79 when that candidate is available on the test checkout.

| Case ID | Behavior | Fixture and action | Expected result |
| --- | --- | --- | --- |
| `GHQ-PY-001` | Graph generation and MCP readback | Pin a tiny Git fixture with a feature, a related implementation in a separate file, and a known line. Start with the feature ID only, run the builder, and follow its implementation evidence through Graphify MCP. | The generated graph reports the pinned source commit. Following the relationship discovers the expected implementation file and line from the feature ID alone. The receipt records successful MCP verification. |
| `GHQ-PY-002` | Deterministic rebuild | Build the same pinned fixture twice in separate temporary output directories using the same locked dependencies. | The two graph files have identical bytes, as do the two receipts. The regular CLI check also accepts the first build. |
| `GHQ-PY-003` | Recover an interrupted replacement | Use the existing #79 fixture with a previously verified pair. Kill the writer in separate runs after the graph replacement and after the receipt replacement but before the journal is retired. Exercise a normal check and a publish retry. Include a second interruption during recovery using #79's existing case. | The next check restores the previous graph and receipt byte for byte. An interrupted rollback can be repeated. A retry publishes a matching new pair and the next run can acquire the lock. |
| `GHQ-PY-004` | Recover an interrupted first publish | Use #79's empty-output fixture. Kill the first writer after the graph replacement, then check and retry. | Recovery removes the incomplete output. The check reports missing evidence, and retry produces a complete pair without manual cleanup. |
| `GHQ-PY-005` | Read and hash the pinned Git blobs | Commit fixture files, then edit the same paths in the working tree. Include a cited file outside `source_files`. | Graph anchors still refer to the committed lines. `source_sha256` hashes the original blob bytes, including the cited non-inventory file. |
| `GHQ-PY-006` | Validate the manifest contract | Table-drive missing required relations, duplicate feature IDs or references, invalid relative paths, duplicate inventory paths, and one accepted plus one rejected boundary for the feature, inventory and per-relation limits. | Invalid inputs fail at validation and the ordinary CLI leaves a sentinel pair untouched. Valid legacy shape and supported limits are accepted. Reuse the existing path and inventory tests. |
| `GHQ-PY-007` | Require one exact source line | Use a committed file with a unique indented line, a near match, and a repeated line. Run the real anchor lookup on the positive case and the CLI on missing and ambiguous anchors. | The unique trimmed match returns the correct one-based line. Missing and ambiguous anchors report zero or multiple matches and preserve prior output. Reuse the anchor unit cases. |
| `GHQ-PY-008` | Link feature evidence through the source inventory | Give two features a shared implementation reference to an inventoried file. Also build a legacy fixture with neither an inventory nor optional implementation links. | Each feature can reach the shared anchor and its file. The anchor has a single `located_in` edge. The legacy manifest still builds with its required evidence relations. Reuse the existing inventory and optional-link cases. |
| `GHQ-PY-009` | Fail on unusable pinned source objects | In an isolated Git fixture, supply a non-commit object as `source_commit`. Then cite a missing path, tree, empty blob, oversized blob and invalid UTF-8 blob under a valid commit. | Each scenario stops before MCP and publication and preserves a prior pair. A valid committed UTF-8 source blob succeeds. |
| `GHQ-PY-010` | Withhold publication when MCP verification fails | Build a fresh graph and use a controlled MCP response for a tool error, wrong source/counts and a missing required relationship. Keep one known-good pair on disk. | Every bad response makes the real verification step fail. The CLI preserves both published files. GHQ-PY-001 supplies the real MCP success path. |
| `GHQ-PY-011` | Detect saved archive drift with `--check` | Start from a valid pair, then alter only the graph in one run and only the receipt in another. Run the real check with no pending recovery journal. | Both runs fail and identify the differing file. The check leaves the altered bytes and the companion file in place. |
| `GHQ-PY-012` | Roll back a write error without a process restart | Reuse #79's injected failure during receipt replacement, with both an existing pair and an empty output directory. Separately supply a directory at the receipt target to exercise the preflight check. | The writer reports failure. A previous pair survives byte for byte, an empty output remains free of partial evidence, and an invalid target is rejected before the graph is replaced. |
| `GHQ-PY-013` | Prevent a competing writer from changing evidence | Use #79's directory-lock regression. Hold the lock in one process while a second invokes publication, then release it and retry. | The competing process cannot change the published bytes. Once the lock is released, a normal publish succeeds. |
| `GHQ-PY-014` | Recognize a renamed repository by stable identity | Reuse #77's stub GitHub responses. Resolve the historical slug to its canonical name and positive numeric ID, then vary the head/base IDs, missing repository identity and source branch. | The renamed repository succeeds and yields the canonical PR URL. An unrelated identity or mismatched branch rejects the observation. |
| `GHQ-PY-015` | Require membership for a historical PR commit | Use the real provenance function with controlled GitHub responses. Test current head, a historical SHA on page two of the commits list and a SHA absent from all pages. | Head is classified as current, the entry on page two as historical, and the absent commit fails. Reuse the historical membership regression. |
| `GHQ-PY-016` | Count only valid reviews on the evidence SHA | Provide approvals on the source and other commits, with later decisions from the same reviewers including requested changes and dismissal. | The observation counts only reviewers whose latest relevant decision is an approval on the exact source SHA. Reuse the exact-review regression. |
| `GHQ-PY-017` | Keep pull-request state and merge SHA separate from source | Simulate a draft, an open PR and a merged PR with distinct source, head and merge SHAs. | Reported state matches the observation. `merge_commit` is populated only for a merged PR and never replaces `source_commit`. Reuse the merge SHA regression. |
| `GHQ-PY-018` | Resolve local, public and private execution modes | Reuse #74's mode tests. Exercise local execution with ordinary CI variables, GitHub public/private/internal events, and a GitHub event with missing or unknown visibility evidence. | The verifier selects the documented mode for valid inputs and fails when a GitHub event cannot establish visibility. |
| `GHQ-PY-019` | Export evidence bytes only from public mode | Use #74's candidate exporter with the same pair for all three modes. Decode the numbered public console chunks and compare the reconstructed bytes with the files. | Public mode emits the original graph and receipt bytes. Private and local mode emit status and source identification without either file payload. |
| `GHQ-PY-020` | Require frozen archive commits and kit contents | Run the real archive verifier against disposable Git history with a good archived ancestor, a source commit outside checkout history and a modified frozen kit file. Stub dependency installation only after the history gates. | The valid history passes the gates. A non-ancestor source or changed frozen kit stops verification before dependencies or a rebuild. |
| `GHQ-PY-021` | Enforce archive catalog ordering and candidate rules | Use the real verifier entry point with a temporary catalog and controlled version verification. Include numeric version ordering, a wrong `latest` value and an older entry with no `source_commit`. | Versions are visited in numeric order. A wrong `latest` or an older unfrozen entry fails. Only the latest entry can use the candidate checkout. |
| `GHQ-PY-022` | Keep frozen source identity separate from candidate identity | Reuse #74's renamed-archive identity test. Give the verifier a frozen source commit and historic slug plus a different checkout SHA and current slug for the candidate. | The frozen manifest uses its historical source identity and performs a check against the archive. The candidate uses the checkout SHA and current identity and writes to staging before check. |

## Bash · Git and workflow integration

Owns the workflow's Git fetch, archive extraction, shell quoting, and failure propagation. Exercise the actual fetch-and-extract step or a shared entry point used by that step. Use disposable Git remotes with known commit objects so these cases can run on an ordinary public Ubuntu runner.

| Case ID | Behavior | Fixture and action | Expected result |
| --- | --- | --- | --- |
| `GHQ-SH-001` | Use exact requested Git pins | Create a bare remote with distinguishable old and new commits. Give the step three distinct full SHAs for the application source, kit, and provenance verifier. Put the branch tip at the newer commit. | The requested source object is available, and the extracted kit and verifier bytes match their pinned commits even though the branch tip points elsewhere. |
| `GHQ-SH-002` | Quote checkout and staging paths | Run the same workflow step with spaces in the checkout path and runner temporary directory while keeping all pins valid. | The step succeeds and the expected files appear under the intended temporary path with their exact contents. |
| `GHQ-SH-003` | Stop on a missing pin | Use a syntactically valid full SHA absent from the temporary remote. Record digests of a sentinel graph and receipt in the existing archive before running the step. | The real step exits nonzero. It produces no extracted kit for the failed attempt, and the previous archive's graph and receipt digests still match. |
| `GHQ-SH-004` | Stop on a malformed source pin before fetching | Use the real workflow step with a manifest that supplies a branch name or short SHA. Record subcommand calls and keep sentinel archive files. | The manifest command fails and the shell stops before fetch, staging or verification. The previous pair stays byte-identical. |
| `GHQ-SH-005` | Propagate archive pipeline failures | Run the workflow step with Actions’ explicit Bash flags. In separate disposable fixtures, omit the expected kit path from a valid pinned tree to fail `git archive`, and deny extraction by passing a regular file as the `tar -C` destination. For the upstream-failure check, use a controlled downstream command that drains stdin and succeeds if needed to isolate `pipefail`. | Each run exits nonzero, even if a downstream process exits successfully in the upstream-failure scenario. The later archive or verifier does not run. The previous pair remains intact. |
| `GHQ-SH-006` | Stop before rebuild when locked dependency setup fails | Exercise the real install step with a command recorder and controlled pip exit status. Fail `pip install` once and `pip check` once. Inspect the arguments and workflow step outcome. | Install uses the extracted lockfile with hashes, wheels and no dependencies. An install failure skips `pip check`. If either command fails, the step fails and the subsequent rebuild is ineligible under the workflow’s default success condition. |

## JavaScript · node:test

Owns the exported data contract at the consumer boundary. Read the raw JSON files without importing the Python builder. Build an independent Node consumer check for the existing export format. Use the Python-generated pair for the valid case and mutate isolated copies for rejected inputs. Use GHQ-PY-008’s richer fixture for source navigation.

| Case ID | Behavior | Fixture and action | Expected result |
| --- | --- | --- | --- |
| `GHQ-JS-001` | Accept a valid exported pair | Read the actual graph and receipt produced by GHQ-PY-001. Supply the expected source SHA from the fixture manifest. | Both files parse. The graph's built-at commit and receipt's source commit match the pin. Receipt node and edge counts match the graph arrays. The graph digest matches, node IDs are unique, and every link endpoint exists. |
| `GHQ-JS-002` | Reject a stale source commit | Keep the valid graph bytes and receipt digest. Change only the receipt's source commit to a different full SHA. | The consumer rejects the pair for a source commit mismatch. |
| `GHQ-JS-003` | Reject a stale graph digest | Make a semantically harmless change to the graph bytes, such as appending a newline. Keep the original receipt. | The consumer rejects the pair for a digest mismatch even though both files still parse. |
| `GHQ-JS-004` | Reject a dangling edge | Change one existing edge endpoint to a nonexistent node ID. Recompute the digest in the copied receipt and keep the edge count the same. | The consumer rejects the pair for a missing edge endpoint. |
| `GHQ-JS-005` | Reject a duplicate node ID | Append a duplicate of an existing node. Update the copied receipt's node count and digest, and keep the links valid. | The consumer rejects the pair for a duplicate node ID even though the digest, counts, and reachability checks are otherwise satisfied. |
| `GHQ-JS-006` | Require both files before reporting evidence | Exercise the planned consumer with one companion absent at a time, as can happen on an interrupted first publish or incomplete copy. | The consumer reports which companion is missing and exposes no project graph. |
| `GHQ-JS-007` | Reject unreadable JSON with a file-specific diagnostic | Truncate each file in separate copies of the valid pair. Leave the other file intact. | Each case fails with a parse error naming the malformed file and produces no accepted graph. |
| `GHQ-JS-008` | Enforce the supported receipt schema and graph shape | Change the receipt `schema_version` to an unsupported version or remove it. Separately replace `nodes` or `links` with a non-array value and keep the receipt digest current. | The consumer rejects unsupported versions and invalid required shapes before making index, count or edge claims. |
| `GHQ-JS-009` | Detect incorrect node or edge totals | Preserve graph bytes, valid references and the original digest. In separate copies, change only the receipt’s `nodes` or `edges` count. | The consumer rejects the mismatched count and identifies which total disagrees with the graph arrays. |
| `GHQ-JS-010` | Require an MCP-verified receipt for verified status | Start from the verified pair and set `mcp_verified` to `false`, remove it, and supply a non-boolean lookalike in separate copies. | None of those variants qualifies as verified evidence. The original receipt with boolean `true` does. |
| `GHQ-JS-011` | Cross-check per-feature evidence totals | Use a graph containing multiple features. Keep the export unchanged and alter one `feature_links` relation count in the receipt. In a separate variant, reassign one feature’s summary to a nonexistent feature ID. | The consumer derives outgoing relation counts from `links` by feature ID and rejects false totals or an unknown feature claim. Whole-graph counts and digest still match. |
| `GHQ-JS-012` | Preserve source navigation from the exported data | Use the valid Python fixture with a shared implementation anchor and inventoried file. Derive paths and one-based lines by following a feature’s links using exported fields. In one copy remove the known anchor’s `source_location` and refresh the receipt digest. | The valid lookup returns the expected repository-relative path and line. The incomplete citation cannot produce a source-link target. File and feature nodes can legitimately have null line locations. |

## Implementation order and evidence

1. Start with `GHQ-PY-001` and `GHQ-JS-001` as one end-to-end handoff. Begin with a feature ID, find the implementation path and line over MCP, and make the exact graph and receipt available to Node. Keep the Python and Node check IDs separate as `python-build` and `node-consume`. Bind the same raw `graph.json` SHA-256 to both Lydite run receipts. The fixture manifest supplies the expected source SHA and the test records the companion receipt digest.
2. Register the Python regressions that already exist at the pinned checkpoints. Use `unittest` and a temporary Git repository for uncovered builder behaviors. File replacement and lock tests use isolated Linux processes. PR review scenarios use stub API responses, with the pinned BART #78 workflow supplying the separate live provenance integration reference.
3. Exercise the checked-in workflow commands for the six Bash cases using a disposable bare Git remote, isolated working trees and the Actions Bash flags `--noprofile --norc -e -o pipefail`. Keep the workflow’s template, provenance and application pins distinct. Check the actual shell exit status and both previous archive file digests. Do not change the historic GitHub workflow just to duplicate its commands in the Vault.
4. Add the remaining `node:test` cases at the consumer boundary. Change one claim at a time and refresh the digest and counts whenever they are irrelevant to the intended failure. Keep the frozen archive as a reference, with test mutations confined to copies.

Use a standard GitHub-hosted Ubuntu runner for public coverage. Record the case ID, exact checkout SHA, command, run ID and attempt, runner/runtime, outcome and evidence digest for shared bytes. Record the commit described by the graph independently of the tested checkout. A `tested_by` graph link identifies a test definition. A Lydite receipt records an execution result. [Lydite run receipt contract](https://github.com/vixttha/Lydite-Test-Vault-Template/blob/fe7b00aa17862d7a01dfd15481594be837bc6d9f/starter/test-vault/evidence.md)

The plan uses frozen v0.0.8 for the baseline, BART #74 and #77 for draft runner/provenance changes, #78 for the draft application workflow, and #79 for draft publication recovery. Revisit the private runner routing with an actual trusted, opted-in private repository and labeled runner when that route is available. The Python runner-mode cases prove the verifier’s behavior, while GitHub evaluates workflow routing.
